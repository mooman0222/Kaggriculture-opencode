## 3. 測り方 (ここを間違えて何度も誤った結論を出した)

- **判定は margin で行う。own では順位がつかない。** own の SE は ±2,600〜2,900 で、上表のどの比較も |t|<1.8。
  own は相手がどれだけ稼いだかに引きずられる。margin はそれが相殺されて SE ±1,300。
  09-17 まで「own 95.4k」を見出しにしていたのは指標の誤り。
- **seed を揃えたペア比較は効かない。** ペア SE 2,960 > 非ペア 1,342。2 つの方策は数手で別の試合に分岐するので、
  同じ seed でも差の分散は各々の分散の和になる。独立 2 標本 t を使う。
- **64 戦で margin 差 4k 未満は区別できない** (差の SE ≈ 1,900)。32 戦では 6k 未満が区別できない。
  09-17 の「すべて SE 内」という判断は 32 戦で出したもので、64 戦にすると初期値の効果が浮き上がった。
- **同レシピの再現 (bc20 vs bc22、別ハード) の差は margin 3.3k (t=1.39)。** これが走り間のノイズ床で、
  サンプリング誤差より大きい。1 本の結果だけで 3k 程度の差を主張してはいけない。
- **val 精度は判断材料にならない。** 最も鮮明な例が bc9k19_ep3: **val option 92.0% (全実行で最高) で閉ループ 49.6k (最低)**。
  bc16 も「val は上がり続けるのに閉ループ 94.4k → 64.6k」。
- **クローン戦なら微差が測れる。** ユニット行動に一切触らない (市場注文だけの) 変更は農場が同一に保たれ、
  E022a は +$18〜64 を 20W0L で検出している。逆にユニット行動を触ると位置がドリフトしてクローンが壊れ、分散が跳ねる。

## 5. 診断で分かった中身

### 5.1 PASS はラベルのバグだった (09-17)
`labels.py::destination_labels` は先読みを当日で打ち切り (`day_end = (t//24+1)*24`)、作業が見つからないと一律
`(現在タイル, PASS)` を書いていた。**ハンドは日雇いで h0 に全消滅・ファーマーも小屋へ転送される**ため、
夕方に目的地へ歩いているユニットは必ずこの分岐に落ちる。

Majkel の生 PASS 62/局 に対し**ラベルは 461/局** (うち 404 は生の行動が MOVE)。h23 で 64%・h22 で 37%。
bc15_ep3 の open-loop 予測 PASS 448/局 は**ラベルの時刻分布と一致**していた = 方策は壊れたラベルを忠実に写していただけ。

修正は「移動中で当日作業なし」を `dest=-1` にして損失から外す。ラベル 461 → 57/局。既存 shard は `rl/fix_pass_labels.py` で修復可能
(誤ラベル集合 `dop==PASS & op∈MOVES` は shard だけから一意に決まる、冪等)。

**得点は動かなかった** (bc15 と bc18 は t=0.91 で区別不能)。価値は「教師の写しとして正しくなったこと」。
なお混合データ (bcw/pq) の PASS は**本物**で、上位陣は実際に 530 回/局 待機している。初期値のラベル修復では PASS は削れない。

### 5.2 給水は問題ない (09-17)
日末に給水済みの株の割合は d8-19 で **自 0.77 / 師 0.75**、2 日放置は両者 0.00。
「WATER 1259 vs 1387」は総手数の差であって、株あたりのカバレッジでは差がない。**この項目は物差しから外す**。

### 5.3 収穫の差の正体は作物構成 (09-17)
d8-19 で畑株数は同じ (53.6 / 52.4) なのに **1 株あたり yield_units 0.58 / 0.82**、実っている株の割合 0.30 / 0.49。

PLANT 要求/局: WHEAT 179.0/152.6、**CARROT 5.8/68.8**、TOMATO 3.5/5.8、**STRAWBERRY 52.0/35.2**、MELON 12.0/12.5。
初収穫までが 2 日の人参を捨て、10 日かかる苺を積んでいる。

除外できた原因: 種切れ (空打ち 0)、`decode_action` の 10 注文上限 (超過 0.3%、捨てられるのは HIRE のみ)、
種在庫・資金・株数の単独要因 (反実仮想で人参買いは復活しない)、市場 pos_w。

**両ヘッドとも open-loop では正しい** (農場ヘッドの PLANT_CARROT 一致率 91.1%、市場ヘッドの人参種予測 93.8 個/局 > ラベル 64.7)。
閉ループでは人参の種在庫が全期間 0。**純粋な state distribution の乖離**で、分岐点は **d6-8 の苺の積みすぎ** (19.5 株 vs 11.1)。
以後、自分の畑に人参 0 株 (師 6 株) の盤面しか現れず、人参を買う文脈が二度と来ない自己強化ループ。

**未解決**: d9 に Majkel が最初の人参を植える引き金は何か。gate は盤面 (tiles) そのもの。

### 5.4 市場ヘッドは買いを過大予測する
`model._mkt_ce(logits, target, n_classes, pos_w)` は市場ラベルの非ゼロを pos_w 倍に重み付けする
(sell/buyp/seed 6・anim 20・hire 8・land 30)。副作用で買い判断が過大になる
(open-loop の買い step: WHEAT 199/154、STRAWBERRY 47.3/29.2、TOMATO 19.7/10.0)。

推論で非ゼロロジットから log(pos_w) を引く `act_common.mkt_argmax` (`play3.py --mkt-debias`) を実装して A/B:
苺の過大購入が pos_w 由来であることは確認できた (種購入 71.2 → 54.0、師 41.5) が、**人参は 6.0 → 10.5 にしか戻らず得点も動かない**。
全ヘッドに適用すると 59.9k に崩壊 — hire/land/anim の pos_w が**意図どおり効いている**裏返しで、**pos_w 自体はバグではない**。
フラグは既定オフの実験用として残置 (`np_act3.py` には未移植)。

### 5.5 critic は死んでいる (09-19)

崩壊後の ckpt を学習なしの診断 (`rl/diag_adv.py`、self-play + tape) で測ると、**V はほぼ定数**:
MC リターン (var ≈ 1.03) に対する R² 0.00〜0.01、v_std 0.08、最終手の V と margin の相関 0.13。
同じ凍結特徴の上で value head を lr 1e-3 で焼き直すと R²_val 0.44〜0.58 = **表現力はある**。
原因は、value head が bc5_ep3 で乱数初期化 (アーキテクチャ不一致) なのに、BC を守る 1e-5 の lr
(200 step ウォームアップ) と 60 step の暖機しか与えられていないこと。**adv ≈ 生の outcome** になり、
pg は baseline なし REINFORCE の高分散更新になる。プローブ・数値は `experiments.md`。

**処方と結果 (`--vlr 1e-3`、09-19)**: critic の相関は 0.13 → **0.55** に上がったが、スケールが 10 分の 1
のまま (R²_mc 0.05) で adv は依然 outcome 支配。崩壊は残り (final own 33.2k、基準 63.1k、shuf 40.4k、
ベース 17.4k)、プロモーションも 0 回だった。

**最後の切り分け = value head 事前学習 (`rl/vpretrain.py`、09-19)**: bc5_ep3 の 8 窓 647k 行で
value head を 2000 step 焼いてから SP3 + `--vlr 1e-3` を再走。事前学習の R²_val は 0.289
(終局行 0.202 / 非終局 0.376、終局行は全体の 6%)、結果は **final own 33.6k で同じ崩壊・昇格 0 回**。
**critic の質を定数 → 0.55 相関 → R²0.29 と 3 水準変えても崩壊は同形**。

**結論: RL は凍結。** BC を守るには実質ゼロの更新しか許されず (shuf = pg 無効でも 63k → 40k)、
向きのある pg は 17〜33k まで壊す。720 手の終端 ±1 と数百コインで決まるミラー戦では、
per-decision の信号がノイズに埋もれており、この規模の PPO では拾えない。
**有効なのは BC (94k) と公開シャシー + テープ (2700 帯)** という 09-18 の結論を追認した。

## 8. 教師について

**教師は 1 位 Majkel1337 のみで確定。** BC は教師分布の条件付き平均を学ぶので、複数の上手い人を混ぜると
誰の戦略でもない平均像になる (混合 1,200 局の BC は demo の平均像 PASS 529/局 を忠実に写していた)。
方策が argmax の単峰モデルである以上、教師分布も単峰にするのが筋。

ただし**混合データを捨てるのではなく初期値に使う**のが正しい (bc9k 1,200 局 → Majkel で fine-tune)。
広いデータで表現を作り、狭いデータで方策を決める。増やすと台無しになるので 1,200 局程度に留める。

天井は Majkel 自身 (LB 3186.6、実戦 own 110k)。bc18 は 94k 帯なので**まだ 16k 下**で、天井は律速ではない。

4. **PPO 崩壊の機構 — 規模不足は棄却、信号と構造の問題** (2026-09-18)。
   サンプル不足と信号の破綻はどちらも同じ形 (単調悪化 + entropy 上昇) を出すので、シャッフル対照で切り分けた。
   **pg を無効化した shuf の方が劣化が半分以下の速さで、信号に従う方が壊れる**。残差の drift (基準 63k → 40k) は entropy 上昇と昇格済み錨が候補。詳細・数値は `experiments.md`。
   残る機構は次の 4 つ (いずれも advantage の正しさを必要としない):

   | # | 機構 | 根拠 | 決着のつけ方 |
   |---|---|---|---|
   | 4a | **クリップは 1 回の歩幅の制限で、総移動距離ではない** | SP3 は 4 minibatch × 50 iter = 200 更新。各 20% 動ける | BC からの累積 KL を iter ごとに記録する (現在は teacher からの KL しか見ていない) |

   **なぜ bc5_ep3 (Policy2) で回したのか、その限界** (09-18):
   崩れた 3 走 (SP1/SP3) の初期値が bc5_ep3 で、4d の測定もすべて bc5_ep3。**過去の失敗をそのまま再現する
   base arm が無いと gd との比較が成立しない**ため、あえて揃えてある。`--greedy-dest` を入れたのも Policy2 の
   経路 (`train.py` / `policy_batch.py`) だけで、**`train3.py` / `policy_batch3.py` には未移植**。
   **限界**: bc5_ep3 は own 63.1k、現行最良の bc18_ep3 は 94k 帯で **30k 下の古い方策**。今回答えるのは
   「探索の設計を替えたら崩壊が止まるか」という**機構の検証**であって、「PPO で我々の最良方策が強くなるか」ではない。
   **移植はしない (棄却)**。Policy3 は joint option を到着まで保持する構造で目的地の扱いが違うため、
   同じ 1 行では済まない上に、探索設計が崩壊の原因でないなら移植して確かめる価値もない。

   **なお `(1−ε)^10` はモデルではなくゲームの性質**で、本線への読み替えは `tracks/chassis.md` 6 節へ。
